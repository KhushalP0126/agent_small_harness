This dataset is genuinely useful — it's the first time you've directly compared "does the harness reshape code" against "does the harness fix correctness," on the same tasks, side by side. And it surfaces a real design flaw, not just a data point: **task 7 is a regression in your harness's own decision logic, and it's worse than it looks.**

**Task 7 is the important finding here — flag it as a bug, not a data point.**

Raw code passed behavior validation — meaning it was *verified correct* against real inputs — and your harness still blocked it for exceeding a complexity threshold. That's the over-strictness failure mode you asked about all the way back in your first message (Q6: "how do I avoid engines becoming too strict and blocking good code"), and now you have a concrete instance of it actually happening. Worse: think about what "fixing" this normally means in your loop — triggering a repair prompt to simplify already-correct code. That's precisely the situation that produced the `key_set` regression on `parse_key_value_lines` a few turns back — an engine finding pushing a *working* solution into a rewrite that risks breaking semantics that weren't broken to begin with. Your policy layer currently can't distinguish "this code is wrong, fix it" from "this code is right but a static heuristic doesn't like its shape," and those need fundamentally different handling:

- **Behavior fails** → block, repair is mandatory, engines drive the repair prompt (current behavior, correct).
- **Behavior passes, static engine finds a quality issue** → this should never be `manual_review_required` at the same severity as a real failure. It should be a *non-blocking* advisory: surface it to the human as "correct but complex, optional simplification available," and only actually trigger a rewrite if a human explicitly requests it. Otherwise you're spending repair budget — and taking on correctness risk — on code that already works, purely to satisfy a heuristic.

This is a concrete, scoped fix: add a `behavior_verified` flag to the policy decision, and have any purely-structural finding (complexity, loop depth, cost) demote to advisory when that flag is true. Parse contract and hazards findings should probably still hard-block regardless (a security/hazard issue in verified-correct code is still worth stopping on), but complexity/branching/cost specifically should not.
