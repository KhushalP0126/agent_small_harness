And it surfaces a real design flaw, not just a data point: **task 7 is a regression in your harness's own decision logic, and it's worse than it looks.**

**Task 7 is the important finding here — flag it as a bug, not a data point.**

Raw code passed behavior validation — meaning it was *verified correct* against real inputs — and your harness still blocked it for exceeding a complexity threshold. That's the over-strictness failure mode you asked about all the way back in your first message (Q6: "how do I avoid engines becoming too strict and blocking good code"), and now you have a concrete instance of it actually happening. Worse: think about what "fixing" this normally means in your loop — triggering a repair prompt to simplify already-correct code. That's precisely the situation that produced the `key_set` regression on `parse_key_value_lines` a few turns back — an engine finding pushing a *working* solution into a rewrite that risks breaking semantics that weren't broken to begin with. Your policy layer currently can't distinguish "this code is wrong, fix it" from "this code is right but a static heuristic doesn't like its shape," and those need fundamentally different handling:

- **Behavior fails** → block, repair is mandatory, engines drive the repair prompt (current behavior, correct).
- **Behavior passes, static engine finds a quality issue** → this should never be `manual_review_required` at the same severity as a real failure. It should be a *non-blocking* advisory: surface it to the human as "correct but complex, optional simplification available," and only actually trigger a rewrite if a human explicitly requests it. Otherwise you're spending repair budget — and taking on correctness risk — on code that already works, purely to satisfy a heuristic.

This is a concrete, scoped fix: add a `behavior_verified` flag to the policy decision, and have any purely-structural finding (complexity, loop depth, cost) demote to advisory when that flag is true. Parse contract and hazards findings should probably still hard-block regardless (a security/hazard issue in verified-correct code is still worth stopping on), but complexity/branching/cost specifically should not.

**Task 5 confirms your standing conclusion, cleanly.** LOC and CC both improved (18→15, 9→7) and behavior still failed — the harness successfully changed the *shape* of the code without touching whether it was *right*. This is good supporting evidence for "engines don't solve semantic reasoning," worth keeping as a reference case alongside `parse_int_list`.

**Task 6 is worth a closer look before you file it as "no improvement."** LOC went from 23 to 25 — the harness made the code *bigger* and didn't reduce complexity at all (8→8), and it still fails. That's not neutral, it's a wasted retry that added surface area without progress. Worth pulling that specific artifact and checking: did the repair prompt target the actual complexity finding, or did it chase a different (possibly lower-priority) finding while complexity sat untouched? If your one-finding-at-a-time routing picked something other than complexity as the "highest priority" finding for that task, that's a prioritization bug in the `RetryBuilder`, not a model capability limit — worth ruling out before concluding the 3B worker just couldn't do it.

**On the 1.5B vs 3B question implicit in this test:** the 3B worker is meaningfully cleaner on easy-to-medium tasks (loop depth stayed at 1 for six of seven tasks, vs. what you'd likely see from 1.5B), but it still produces the same branch-heavy pattern on hard tasks (CC 9, 8, 12 on tasks 5–7) that your engines exist to catch. That tells you upgrading the worker model buys you fewer trivial engine triggers on easy tasks, but doesn't change the fundamental shape of the hard-task problem — which is still "harder tasks produce branch-heavy first drafts that need either decomposition or architect intervention." Not a strong enough signal to justify switching production workers yet; more useful as confirmation that your engine/aggregation investment is the right place to keep spending effort rather than chasing a bigger small-model.

I checked `validation/behavior.py` specifically for this, and it surfaced something worth leading with — a real, previously-undiscussed gap that explains a bug we already found.

## 1. Behavior validation can't test classes at all — this is why `PongState` broke undetected

The sandbox is actually well-built: subprocess isolation via `multiprocessing`, a timeout, a whitelisted `SAFE_BUILTINS` set, and blocked dangerous calls (`eval`, `exec`, `open`, `__import__`). Good security posture. But `BLOCKED_NODES` includes `ast.ClassDef` — any generated source containing a class definition gets rejected outright by `_validate_runtime_ast` before behavior checking even runs. `PongState`, `Ball`, and `Paddle` are all classes. That means the exact bug we found earlier — `PongState.update_score` referencing `self.score1`/`self.score2`, which don't exist in its own `__init__` — is structurally *unreachable* by behavior validation. Not "the test didn't catch it," but "the validator can't test this kind of code at all." Worth adding: a second validation tier that can safely instantiate a class in the sandbox and call its methods with representative arguments, still under the same process-isolation/timeout discipline, so stateful composite code gets the same coverage pure functions get.

## 2. A truncation-aware continuation path, instead of full-context resend

Right now if the architect's response gets cut off (like the Pong integration truncation we found), the only recovery is resending the entire plan packet + all accepted contract sources + the full broken draft — 65K characters — with an instruction to "try again." Add a cheap pre-check: if a response has unbalanced brackets/parens or no closing fence, treat it as `truncated` (a distinct category from `invalid_syntax`) and send a small continuation prompt — just the tail of the broken draft plus "continue from exactly this point" — instead of the full context. This is a new code path, not a fix to an existing one.

## 3. Per-run cost/token telemetry

Nothing in `metadata.json` tracks tokens spent or API cost. Given DeepSeek calls cost real money and we just found a single run burning a 65K-character prompt, this is worth surfacing as its own artifact field — tokens in/out and estimated cost per contract, per repair round, per run. Right now the only way to notice a run got expensive is to manually read `retry_prompt_chars` in `attempt_timeline.json`, which isn't cost, just a proxy for it.

## 4. Regression detection in the historian, not just accumulation

`historian.py` already has `aggregate_run_stats` and `successful_templates` — it accumulates history well but doesn't compare against it. Add a check that runs automatically at the end of a session: "for specs with a similar shape (same `task_type`, similar component count), did this run's violation count / retry count / final status get worse than the historical median?" Right now that comparison only happens if a human manually runs `review-run` and eyeballs it.

## 5. Cross-file generation support (a real, not just stated, gap)

The README's "Current Direction" already says multi-file generation is the goal, but I want to flag what's concretely missing to get there rather than just repeat that intention: there's no import-graph resolver and no cross-file symbol table anywhere in the codebase. `spec.files` only ever contains one entry in both example specs. When you do build this, it'll need the same shared-IR fix from the compiler discussion — a symbol table that spans files, not just spans engines within one file — so it's worth sequencing after that architectural work rather than before it.

## 6. A prompt-size budget, enforced structurally, not by hoping the model behaves

Related to #2 but more general: nothing currently stops a prompt from growing unbounded across repair rounds. A hard ceiling (e.g., "if the assembled prompt exceeds N tokens, drop the oldest failed-attempt context first, then drop full contract sources in favor of signatures-only") would prevent the 65K-character case from recurring in other failure shapes, not just the truncation one.

**One thing worth flagging about the diagram itself:** it only represents one of two real execution paths. The path it draws — single draft, retry, escalate — matches `run_worker_limit.py`-style general code tasks. The path that actually ran for Pong (`kernel/function_contracts.py` + `ContractQueue` + a separate architect integration step) is materially different — sequential per-contract generation with its own repair loop, then a whole separate synthesis-and-validate pass for integration — and isn't represented in the README diagram at all. If someone read only the diagram, they'd have no idea the contract-queue path (which is what actually produces app-scale output like Snake/Pong) exists or that it has its own failure modes.

**Net read:** the "verify and reject" half of the pipeline (parse gate → engines → policy → repair-directive generation → artifacts/historian) is genuinely solid and battle-tested against a real run. The "generate and repair" half is functionally wired end-to-end but has the specific known gaps we've already named: token budgets sized for single functions applied to whole-module synthesis, stagnation detection cruder than the signal already available, and retry prompts that grow instead of staying scoped as failures compound.
